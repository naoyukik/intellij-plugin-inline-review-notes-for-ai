# プロジェクトワークフロー

## 基本原則

1. **計画が唯一の真実:** すべての作業は `plan.md` で追跡すること
2. **技術スタックは意図的に管理する:** 技術スタックへの変更は実装前に `tech-stack.md` に記録すること
3. **テスト駆動開発:** 機能の実装前に単体テストを書くこと
4. **高いコードカバレッジ:** すべてのモジュールで 80% 超のカバレッジを目指すこと
5. **ユーザー体験を最優先:** すべての判断はユーザー体験を優先すること
6. **非対話かつ CI を意識する:** 対話型コマンドは避けること。ウォッチモードのツール（テスト、リンター）には `CI=true` を使い、1 回だけ実行されるようにすること
7. **トラック命名:** トラック名（およびそのディレクトリ名）のプレフィックス番号は、対応する GitHub Issue 番号（チケット番号）に合わせること。例: Issue #3 なら `003-xxx` とし、3 桁ゼロ埋めにする

## リポジトリ規約

### 言語ポリシー

- `spec.md`、`plan.md`、`workflow.md`、レポート、AI との会話は日本語で書くこと
- コード内コメントは、複雑なロジックを説明する場合のみ日本語で書くこと

### テスト要件

- 最低目標は 80% 以上のカバレッジ
- 各機能に対応する単体テストを用意すること
- 変更後はテスト結果を直接確認し、推測だけで完了扱いにしないこと
- 各タスクのコミット前に、プロジェクトで設定された静的解析タスクを実行すること。`detekt` がこのリポジトリで利用可能なら `./gradlew detekt` を実行すること

### コミット方針

- 各タスク完了後にコミットすること
- コミットメッセージは `AGENTS.md` に定義された Conventional Commits ルールに従うこと

### 検証方針

- ユーザーによる手動検証が必要なタスクは、ユーザーが明示的に承認するまで完了扱いにしないこと
- 実装が正しく見えても、挙動が検証されるまでは未完了として扱うこと
- 手順より効率を優先しないこと

- Kotlin リファレンス: https://kotlinlang.org/docs/
- IntelliJ Plugin リファレンス: https://plugins.jetbrains.com/docs/

## タスクワークフロー

すべてのタスクは、次の厳密なライフサイクルに従うこと:

### 標準タスクワークフロー

1. **タスクを選択:** `plan.md` から次に実行可能なタスクを順番に選ぶ

2. **進行中にする:** 作業を始める前に `plan.md` を編集し、タスクの状態を `[ ]` から `[~]` に変更する

3. **失敗するテストを書く (Red フェーズ):**
   - 機能または不具合修正のために新しいテストファイルを作成する
   - そのタスクの期待動作と受け入れ条件を明確に定義する単体テストを 1 つ以上書く
   - **重要:** テストを実行し、想定どおり失敗することを確認する。これが TDD の「Red」フェーズである。失敗を確認するまで先へ進まないこと

4. **テストを通すように実装する (Green フェーズ):**
   - 失敗しているテストを通すために必要最小限のアプリケーションコードを書く
   - テストスイートを再実行し、すべてのテストが通ることを確認する。これが「Green」フェーズである

5. **リファクタリング (任意だが推奨):**
   - テストが通っている安全な状態で、実装コードとテストコードを整理し、重複を減らし、可読性や性能を改善する。ただし外部動作は変えないこと
   - リファクタリング後に再度テストを実行し、引き続き通ることを確認する

6. **カバレッジと静的解析を確認:** プロジェクトが選択したツールでカバレッジレポートを実行し、設定済みの静的解析タスクを実行する。`detekt` が利用可能なら `./gradlew detekt` を実行する。例えば Python プロジェクトなら次のようになる:
   ```bash
   pytest --cov=app --cov-report=html
   ```
   新規コードの目標: 80% 超のカバレッジ。具体的なツールやコマンドは言語とフレームワークにより異なる

7. **逸脱を記録:** 実装が技術スタックと異なる場合:
   - **実装を停止する**
   - 新しい設計を `tech-stack.md` に更新する
   - 変更内容を説明する日付付きメモを追加する
   - 実装を再開する

8. **コード変更をコミット:**
   - タスクに関連するすべてのコード変更をステージする
   - 例として `feat(ui): Create basic HTML structure for calculator` のような、明確で簡潔なコミットメッセージを提案する
   - テストと静的解析が通った後にのみコミットする

9. **タスクのコミット SHA を取得して記録:**
   - **Step 10.1: プランを更新:** `plan.md` を読み、完了したタスクの行を見つけて状態を `[~]` から `[x]` に更新し、直前に完了したコミットのコミットハッシュの先頭 7 文字を追記する
   - **Step 10.2: プランを書き戻す:** 更新後の内容を `plan.md` に書き戻す

10. **プラン更新をコミット:**
    - **Action:** 変更した `plan.md` をステージする
    - **Action:** `conductor(plan): Mark task 'Create user model' as complete` のような説明的なメッセージでこの変更をコミットする

### リポジトリ固有のタスクフロー

このリポジトリでは、作業は通常次の流れで進める:

1. **フェーズ 0 - 調査と計画:** `autonomous-researcher` を使って関連コードを調査し、`evidence_report.md` を作成し、`plan.md` の残り項目を具体的なファイル名、想定行範囲、意図する変更内容に書き換える
2. **タスクごとのサイクル:** 各実装タスクについて、`実装 -> テスト -> 静的解析 -> コミット` を繰り返す
3. **フェーズ終了:** 各フェーズは必ず `Conductor - ユーザー手動検証` と、その後のフェーズ・チェックポイント・ワークフローで終えること

### 標準フェーズ構成

トラックがフェーズ分割を採用している場合は、フェーズ構造を明示的に保つこと:

- フェーズ 0 は Discovery と詳細設計である
- フェーズ 0 には、調査、計画の精緻化、環境確認、手動検証タスクを含めること
- フェーズ 0 のevidence_reportがユーザーによって承認されたのち、evidence_reportを元にフェーズ１以降のタスクを必要な内容に加筆修正すること。
- 以降のフェーズには、その機能に必要な具体的な実装タスクのみを含めること
- 各フェーズの終了時には、`./gradlew test`、利用可能なら `./gradlew detekt` などの設定済み静的解析タスク、そして手動検証を実行してから、コミットを行う。

### フェーズ完了検証とチェックポイント作成プロトコル

**トリガー:** このプロトコルは、`plan.md` の中でフェーズ終了にもなるタスクを完了した直後に実行する

1. **プロトコル開始を宣言:** フェーズ完了と、検証およびチェックポイント作成プロトコルの開始をユーザーに伝える

2. **フェーズ変更のテスト対象を確保:**
    - **Step 2.1: フェーズ範囲を特定:** このフェーズで変更されたファイルを特定するため、まず開始点を見つける必要がある。`plan.md` を読み、前フェーズのチェックポイントの Git コミット SHA を探す。前回のチェックポイントがなければ、範囲は最初のコミット以降のすべての変更である
    - **Step 2.2: 変更ファイルを列挙:** `git diff --name-only <previous_checkpoint_sha> HEAD` を実行し、このフェーズで変更されたすべてのファイルを正確に取得する
    - **Step 2.3: テストを確認・作成:** 一覧にある各ファイルについて:
        - **重要:** まず拡張子を確認し、非コードファイル（例: `.json`、`.md`、`.yaml`）は除外する
        - 残った各コードファイルについて、対応するテストファイルが存在するか確認する
        - テストファイルがなければ、必ず新規作成する。テストを書く前に、まずリポジトリ内の他のテストファイルを調べて、正しい命名規則とテストスタイルを把握すること。新しいテストは、このフェーズのタスクで説明された機能を検証しなければならない（`plan.md` を参照）

3. **自動テストと静的解析を先回りデバッグ付きで実行:**
    - 実行前に、テストと静的解析に使う正確なシェルコマンドをユーザーに宣言しなければならない
    - **例:** 「これから自動テストスイートと静的解析を実行してフェーズを検証します。**Commands:** `./gradlew test` と `./gradlew detekt`」
    - 宣言したコマンドを実行する
    - テストが失敗した場合は、ユーザーに知らせてデバッグを始めること。修正案の提示は最大 2 回まで。2 回目の修正後も失敗が続くなら、そこで停止し、失敗が継続していることを報告してユーザーの指示を求めること

4. **詳細で実行可能な手動検証計画を提案:**
    - **重要:** 計画を作る前に `product.md`、`product-guidelines.md`、`plan.md` を調べ、完了したフェーズのユーザー向けゴールを把握すること
    - 完了したフェーズの検証手順を、ユーザーが順番に実施できるようなステップバイステップの計画として生成すること

5. **ユーザーの明示的なフィードバックを待つ:**
    - 詳細な計画を示した後で、ユーザーに次の確認を求める: **\"Does this meet your expectations? Please confirm with yes or provide feedback on what needs to be changed.\"**
    - **停止**し、ユーザーの応答を待つ。明示的な yes または確認なしには先へ進まないこと

6. **チェックポイントコミットを作成:**
    - 変更があればすべてステージする。ここで変更がなければ空コミットに進む
    - `conductor(checkpoint): Checkpoint end of Phase X` のような明確で簡潔なメッセージでコミットする

## 品質ゲート

タスクを完了としてマークする前に、次を確認すること:

- [ ] すべてのテストが通る
- [ ] コードカバレッジが要件を満たしている（80% 超）
- [ ] コードがプロジェクトのコードスタイルガイド（`code_styleguides/` で定義）に従っている
- [ ] すべての公開関数・メソッドにドキュメントがある（例: docstring、JSDoc、GoDoc）
- [ ] 型安全性が確保されている（例: 型ヒント、TypeScript の型、Go の型）
- [ ] リントや静的解析のエラーがない（プロジェクトで設定されたツールを使用）
- [ ] 必要な場合はドキュメントが更新されている
- [ ] セキュリティ脆弱性を新たに導入していない

## テスト要件

### 単体テスト
- すべてのモジュールに対応するテストを用意すること
- 適切なセットアップ/ティアダウン機構（例: fixture、beforeEach/afterEach）を使うこと
- 外部依存をモックすること
- 成功ケースと失敗ケースの両方をテストすること
- 機能レベルのテストは `plan.md` のタスクに合わせて維持すること

### 統合テスト
- 完全なユーザーフローをテストすること
- データベーストランザクションを検証すること
- 認証と認可をテストすること
- フォーム送信を確認すること

## トラック管理

### トラック作成

1. `conductor/tracks.md` にトラックを登録する
2. `conductor/tracks/<track_id>/` を作成する
3. そのフォルダに `index.md`、`spec.md`、`plan.md`、`metadata.json` を置く
4. `<track_id>` を含む名前の Git ブランチを作成する

### トラック実行

- トラックの `plan.md` を唯一の真実として使うこと
- トラック名は Issue 番号のプレフィックス規約に揃えること
- 作業内容が変わったら、記憶やチャット履歴に頼らずプランを更新すること

## コードレビュー手順

### セルフレビュー・チェックリスト
レビュー依頼前に次を確認する:

1. **機能性**
   - 機能が仕様どおりに動作する
   - エッジケースが処理されている
   - エラーメッセージがユーザーフレンドリーである

2. **コード品質**
   - スタイルガイドに従っている
   - DRY 原則を適用している
   - 変数名・関数名が明確である
   - 適切なコメントがある

3. **テスト**
   - 単体テストが十分である
   - 統合テストが通る
   - カバレッジが十分である（80% 超）

4. **セキュリティ**
   - ハードコードされた秘密情報がない
   - 入力検証がある
   - SQL インジェクション対策がある
   - XSS 対策がある

5. **パフォーマンス**
   - データベースクエリが最適化されている
   - 画像が最適化されている
   - 必要な箇所でキャッシュが実装されている

## コミットガイドライン

### メッセージ形式
```
<type>(<scope>): <description>
```

### 種別
- `feat`: 新機能
- `fix`: 不具合修正
- `docs`: ドキュメントのみ
- `style`: フォーマット、セミコロン不足など
- `refactor`: 不具合修正でも新機能追加でもないコード変更
- `test`: 不足しているテストの追加
- `chore`: 保守作業

## 完了の定義

タスクが完了とみなされる条件:

1. すべてのコードが仕様どおりに実装されている
2. 単体テストが書かれ、通っている
3. コードカバレッジがプロジェクト要件を満たしている
4. 必要に応じてドキュメントが整備されている
5. すべての設定済み lint / static analysis に通っている
6. 必要に応じてモバイルで美しく動作する
7. 実装メモが `plan.md` に追加されている
8. 正しいメッセージで変更がコミットされている
9. タスク要約を含む Git note がコミットに添付されている
